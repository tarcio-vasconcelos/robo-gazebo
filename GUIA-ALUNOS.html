1. Instalação, do zero

O que você vai usar

O Gazebo simula o robô, a parede, o movimento e o sensor. O Python executa a estratégia escrita pelos alunos. Um arquivo SDF descreve o cenário. Não é necessário instalar ROS para esta atividade.

Adotamos Gazebo Harmonic para fixar a combinação de versões: Sim 8, Transport 13 e mensagens 10. Existem versões posteriores; misturar as bibliotecas de versões diferentes pode impedir os programas de funcionar.

Como os grupos usarão computadores próprios, o caminho comum é Docker + navegador. O Docker executa um Ubuntu preparado; o navegador mostra a tela desse Ubuntu. Não se trata de uma versão web do Gazebo: a simulação continua rodando localmente no computador.

Como referência de planejamento, reserve 4 núcleos, 6 GB de memória para o Docker e aproximadamente 15 GB livres. São estimativas para este pacote, não requisitos oficiais universais. Em computadores com 8 GB de RAM total pode haver lentidão. O primeiro download exige internet; a imagem pode ocupar vários GB. Faça a instalação antes da aula.

Opção A — Mac, Windows ou Linux com Docker

A1. Instalar e abrir o Docker

• Mac: baixe o Docker Desktop para o processador correto, Apple Silicon (M1/M2/M3/M4 etc.) ou Intel. Arraste o aplicativo para Aplicativos e abra. Siga a instalação oficial para Mac.

• Windows: instale o Docker Desktop com o mecanismo WSL 2 e contêineres Linux. Se o instalador pedir atualização do WSL ou reinício, conclua essas etapas. Siga a instalação oficial para Windows. Se necessário, execute wsl --install em PowerShell como administrador e reinicie antes de continuar.

• Linux: use Docker Engine e o plugin Compose ou Docker Desktop. O usuário precisa conseguir executar docker info.

Abra o aplicativo Docker Desktop e espere informar que o mecanismo está funcionando. Ele precisa continuar aberto durante a atividade. No Mac deste professor foi encontrado um comando Docker antigo, mas não o aplicativo Docker Desktop em Aplicativos; o Compose também estava indisponível. Instale ou reinstale o Docker Desktop antes de seguir.

A2. Abrir um terminal na pasta correta

Extraia o ZIP antes de executar. Evite OneDrive/iCloud e pastas de rede se houver problemas de compartilhamento; prefira uma pasta local. Não execute diretamente de dentro do ZIP.

• Windows: abra a pasta no Explorador, clique na barra de endereço, digite powershell e pressione Enter.

• Mac: abra Terminal, digite cd com um espaço, arraste a pasta extraída para a janela e pressione Enter.

• Linux: abra um terminal na pasta extraída pelo gerenciador de arquivos.

A pasta correta contém compose.yaml, README.md e a pasta alunos.

Confira:

docker info
docker compose version

Se docker compose version informar que compose não é um comando, instale ou reinstale o Docker Desktop. Se aparecer que não consegue conectar ao mecanismo, abra o Docker Desktop e aguarde. Não adianta repetir a construção antes de ele funcionar.

A3. Preparar o ambiente

docker compose up -d --build

Este comando baixa o Ubuntu e instala o Gazebo dentro do contêiner. Na primeira vez demora mais. Aguarde voltar ao prompt sem mensagem de erro. Em dias posteriores, basta docker compose up -d.

Confira:

docker compose ps
docker compose exec sim gz sim --versions
docker compose exec sim /usr/bin/python3 -c "from gz.transport13 import Node; from gz.msgs10.laserscan_pb2 import LaserScan; print('Python e Gazebo disponíveis')"

O serviço sim deve estar em execução. A versão do Sim deve ser 8.x. O terceiro comando deve imprimir a mensagem final sem erro de importação.

A4. Abrir a tela

Acesse a tela local do ambiente. Se necessário, clique em Connect. Inicialmente aparece uma área de trabalho simples; o Gazebo só abre no próximo guia.

O pacote usa a arquitetura nativa do computador: ARM64 em Macs Apple Silicon e AMD64 em computadores Intel/AMD. O repositório do Gazebo oferece os pacotes necessários para ambas as arquiteturas. A renderização é feita por software para evitar exigir repasse da placa gráfica. Isso precisa ser testado em cada perfil de máquina antes da aula; não há garantia de desempenho uniforme. A versão inicial forçava AMD64 e apresentou travamento da janela no Mac Apple Silicon; essa configuração foi corrigida.

O acesso da tela fica restrito ao próprio computador (127.0.0.1). A pasta extraída é compartilhada com o ambiente: edite alunos/solucao.py no seu editor habitual e salve; não é necessário reconstruir a imagem a cada edição.

Opção B — Ubuntu 24.04 em computador Intel/AMD

É a alternativa com menos camadas e a primeira escolha para um laboratório Linux. A instalação direta deste pacote exige Ubuntu 24.04 amd64. Não execute o instalador no macOS, PowerShell, Ubuntu ARM ou outra distribuição.

No terminal, dentro da pasta do pacote:

bash scripts/instalar-ubuntu.sh
gz sim --versions
/usr/bin/python3 -c "from gz.transport13 import Node; print('Integração disponível')"

O instalador pedirá sua senha para instalar os pacotes. A senha não aparece enquanto você digita. Ele usa o repositório oficial do Gazebo; confira os comandos em scripts/instalar-ubuntu.sh se desejar.

Nesse caminho, substitua os comandos Docker do próximo guia por:

bash scripts/iniciar.sh
bash scripts/executar.sh

Cada comando deve ficar em seu próprio terminal. O Gazebo abre como aplicativo, sem navegador.

Instalação nativa no Mac

A documentação do Harmonic fornece instalação por Homebrew com brew tap osrf/simulation, brew trust osrf/simulation e brew install gz-harmonic. Ela anuncia pacotes prontos para macOS Sequoia em Apple Silicon e descreve o servidor gz sim -s; em outras versões pode haver compilação longa. O Mac consultado usa macOS 26.6.2, fora dessa combinação anunciada. Por isso, essa não é a rota principal deste pacote. Os scripts de instalação e execução direta aqui são para Ubuntu; não presumem que os bindings Python do Homebrew estejam configurados.

Se um computador não conseguir executar

Faça o piloto antes de atribuir nota. Primeiro tente Ubuntu nativo em uma máquina disponível. Se um grupo precisar usar um computador de colega, todos ainda devem participar da edição, dos experimentos e da explicação. Evite transformar problemas de instalação em critério de desempenho acadêmico.

No fim do trabalho com Docker:

docker compose down

Isso encerra o ambiente. Os arquivos de código e os resultados salvos na pasta permanecem no computador.

2. Primeira execução e operação

Antes de começar

Conclua a instalação. Deixe abertos dois terminais na pasta do pacote e, no caminho Docker, a tela do navegador. Comandos docker compose exec são digitados no terminal do seu computador, não na barra de endereço do navegador nem no console do Python.

Passo 1 — Abrir o cenário

No terminal A:

docker compose exec sim bash scripts/iniciar.sh

O terminal fica ocupado: isso é esperado. Na tela do navegador aparecerá o Gazebo com um robô azul, uma parede vermelha e uma marca verde no chão. Aguarde a cena carregar.

O script usa -r, portanto a simulação começa rodando. Na interface, o controle Play/Pause pode interromper e retomar o tempo. A missão só avança com o tempo de simulação rodando. O sensor fica na frente do robô, voltado para a parede.

Se a câmera não mostrar a cena, procure o modelo robo na árvore de entidades, selecione e use o recurso de mover a câmera para a seleção, disponível no menu de contexto. A navegação da câmera também pode ser feita com o mouse. Consulte o guia oficial da interface.

Passo 2 — Conferir se o sensor funciona

No terminal B:

docker compose exec sim gz topic -l
docker compose exec sim gz topic -e -t /desafio/scan

O primeiro comando deve incluir /desafio/scan, /desafio/odom e /desafio/cmd_vel. O segundo imprime mensagens continuamente; procure ranges, com valores próximos de 2.65 m no cenário inicial. Use Ctrl+C para parar apenas essa visualização. O tópico de contato pode ficar silencioso enquanto não existe contato.

Os scripts configuram GZ_PARTITION=estacionamento01; no Docker isso já está no ambiente. No Ubuntu direto, antes dos comandos de diagnóstico gz topic, execute export GZ_PARTITION=estacionamento01 nesse terminal.

Passo 3 — Executar o código inicial

No terminal B:

docker compose exec sim bash scripts/executar.sh

O robô fica parado. O arquivo inicial retorna zero para qualquer distância. Use Ctrl+C depois de conferir; o programa envia uma parada e grava os resultados. O limite normal é 45 segundos de simulação, contados a partir da primeira leitura recebida pelo executor.

Não deixe esse executor rodando ao iniciar outro. Somente um programa pode comandar o robô por vez.

Passo 4 — Demonstração do professor

Disponível apenas no pacote completo. Encerre o executor anterior e inicie uma tentativa nova pelo procedimento de reinício abaixo. No terminal B:

docker compose exec sim bash scripts/executar.sh --solucao professor/referencia.py --saida resultados/demo

Espera-se que o robô avance, reduza a velocidade e pare na faixa. A saída deve terminar com "status": "sucesso". Essa é uma expectativa a validar na máquina, não uma execução previamente comprovada neste material.

A marca verde indica onde a frente do robô deve ficar; não é a posição do centro dele. A distância é medida da frente à parede. A meta é um intervalo de 0.27 a 0.33 m.

Passo 5 — Editar e repetir

Abra alunos/solucao.py em um editor, altere somente decidir_velocidade, salve e reinicie a tentativa. Não é necessário reiniciar o Docker por edição. O Python relê o arquivo ao iniciar o executor.

Registre cada ensaio com um nome diferente:

docker compose exec sim bash scripts/executar.sh --saida resultados/grupo01-teste01

Arquivos existentes com o mesmo nome serão substituídos. Os resultados ficam na pasta local resultados, em CSV (leituras e comandos) e JSON (resumo). O CSV pode ser aberto em um editor ou importado em uma planilha.

Como reiniciar corretamente

1. No terminal B, pressione Ctrl+C se o executor ainda estiver rodando e espere o resumo final.

2. No terminal A, pressione Ctrl+C para fechar o Gazebo e espere o comando terminar.

3. Inicie novamente docker compose exec sim bash scripts/iniciar.sh no terminal A.

4. Aguarde o cenário aparecer; confira que o robô voltou à posição inicial.

5. Execute novamente a estratégia no terminal B.

Esse procedimento recarrega o mundo, a velocidade e os relógios. Evita as ambiguidades de diferentes botões Reset da interface. Não use Reset durante uma tentativa avaliada.

Parada imediata

Ctrl+C no executor deve enviar velocidade zero. Se o programa travar ou a sessão cair, abra outro terminal e use:

docker compose exec sim bash scripts/parar.sh

Se necessário, use Pause na interface ou feche o Gazebo no terminal A. Comandos de velocidade podem persistir se um processo for encerrado abruptamente; o comando de parada não substitui encerrar um controlador ainda ativo que continue publicando movimento.

Desafio 01 — Estacionamento de precisão

Missão

Vocês programarão um robô que se aproxima de uma parede e estaciona sem encostar. A cada leitura do sensor, o programa deve decidir com que velocidade avançar. O robô já está alinhado; não é necessário fazer curvas.

Sucesso: distância frontal entre 0.27 e 0.33 m, velocidade medida de no máximo 0.01 m/s, comando zero e permanência nessas condições por 2 segundos de simulação, sem colisão durante a tentativa. O limite é 45 segundos de simulação. O cronômetro da tentativa começa na primeira leitura recebida pelo executor.

O objetivo principal é escrever uma estratégia compreensível, testar hipóteses e explicar as escolhas. A instalação será conferida antes da avaliação.

Organização

Grupos de 3 ou 4 integrantes. Alternem quem edita o código, quem executa e registra os ensaios e quem revisa o raciocínio. Todos devem conseguir explicar a solução.

Pré-requisitos: variáveis, operações aritméticas, if/elif/else, funções, parâmetros e return. O executor já contém a repetição que chama a função continuamente. Não é necessário escrever código de comunicação com o Gazebo.

O que editar

Somente alunos/solucao.py, na função:

def decidir_velocidade(distancia):
    return 0.0

• distancia é um número em metros, medido da frente do robô até a parede.

• Retorne uma velocidade entre 0.0 e 0.5 m/s.

• 0.0 significa parar. Valores maiores significam avançar mais depressa.

• Não há marcha a ré neste desafio. Se passar da faixa, reinicie e corrija a estratégia.

• A função é chamada a cada nova leitura, aproximadamente 20 vezes por segundo de simulação.

• A função deve retornar rapidamente. Não coloque input(), sleep() ou um laço infinito nela.

Exemplo de interpretação das unidades: 0.80 m são 80 cm; 0.30 m são 30 cm; 0.03 m são 3 cm. A velocidade pedida é em metros por segundo, não uma porcentagem da potência do motor.

Regras

1. A decisão deve usar a distância recebida. Não use espera por tempo fixo, contagem de chamadas ou coordenadas conhecidas da parede.

2. Não altere o mundo, os sensores, a infraestrutura ou os limites de velocidade para realizar a avaliação.

3. Não envie comandos por outro programa enquanto o executor estiver ativo.

4. Toda tentativa começa com o mundo recarregado pelo procedimento do guia.

5. Registre pelo menos cinco ensaios e explique pelo menos duas mudanças feitas na estratégia.

6. Declare materiais consultados e ferramentas usadas, conforme a política da disciplina.

Etapas sugeridas

Etapa 1 — Entender. Execute o programa inicial e explique por que ele fica parado. Observe a leitura do sensor e localize as unidades.

Etapa 2 — Primeira estratégia. Façam o robô avançar enquanto estiver longe e parar perto da meta. Escolham uma velocidade inicial conservadora.

Etapa 3 — Melhorar. Investiguem se vale a pena reduzir a velocidade perto da parede. A frenagem não é instantânea; o robô pode continuar se movendo depois de receber zero.

Etapa 4 — Testar. Repitam os ensaios com nomes diferentes de saída e comparem o tempo simulado e a distância final. Identifiquem o que mudou e o efeito observado.

Etapa 5 — Explicar. Preparem uma demonstração de até 5 minutos e a ficha do grupo preenchida.

Níveis de realização

• Essencial: cumprir a missão no cenário de treino.

• Robusto: cumprir também em três cenários com distâncias iniciais diferentes, mantendo o robô alinhado e o sensor sem ruído.

• Eficiente: reduzir o tempo sem perder precisão ou robustez.

Não serão introduzidos giros, obstáculos laterais, falhas de sensor ou ruído surpresa nesta avaliação. Extensões desse tipo são atividades separadas.

Entrega

• Arquivo alunos/solucao.py, com nomes de todos os integrantes em comentário.

• Ficha do grupo preenchida, com tabela de pelo menos cinco ensaios.

• CSV e JSON correspondentes aos ensaios relatados.

• Explicação breve das decisões e de uma limitação conhecida.

• Demonstração e explicação individual de uma parte da estratégia.

Avaliação — 10 pontos

CritérioPontosEvidência
Cumprimento da missão5.0Duas tentativas no cenário de treino; cada sucesso vale 2.5.
Robustez2.0Uma tentativa em cada uma de três variações: 0, 1, 2 ou 3 sucessos valem 0, 0.7, 1.3 ou 2.0.
Clareza, experimentação e explicação2.0Código compreensível, registros e justificativas: 1.0; explicação individual: 1.0.
Eficiência1.0Entre tentativas bem-sucedidas de treino: média até 15 s vale 1.0; acima de 15 até 25 s vale 0.5; acima de 25 s vale 0. Sem sucesso: 0.

Os limites de eficiência devem ser confirmados pelo professor no piloto e publicados antes da atividade. Problemas de instalação ou interrupções comprovadas do simulador serão tratados como incidentes e terão a tentativa refeita.
